0. 写在开头

一个优秀的Agent/eval infra必定具备了RL侧的所需要的充分。所以本文将2.harbor以及3.verifiers开始分析并在这两者其中穿插着他们各自对于RL-post train 的feature，给大家一个清晰且宏观的大致思维框架。然后着重分析4去了解smile对于训练agent的解决方案，来告诉大家环境/agent/cli应该如何和RL-infra交互以及优化训练。最后5.针对以上三点我给出了我认为的一个优秀的agent infra应该具备的要素，以及RL-infra在未来可能的两种option。

Harbor——agent评测 / RL 环境harness

Harbor 这一套harness只回答一个问题：「设定task和agent，告诉我它做得怎么样。」我们可以用六个抽象去表述他——Task（指令 + 文件）、Environment（统一sandbox，本地 Docker 或云厂商）、Agent（被测的脚手架）、Verifier（跑测试 → 产出 reward）、Trial（一次产生一个 reward 的 rollout）、Job（一整批 trial）。Harbor 在循环里的座位是环境 / 评测侧：跑agent、给它打分。它自己的口号替整个 wiki 把话说完了——「a trial is a rollout that produces a reward」（trial 就是一次产生 reward 的 rollout）。

verifiers——RL 环境 + 评测库

verifiers是一个把自包含 RL 环境写成小 Python 模块的库。每个环境 = 数据集 + rollout harness + Rubric（一组带weight的奖励函数），通过 SingleTurnEnv、MultiTurnEnv、ToolEnv 等类暴露。这些环境发布到 Environments Hub（2,500+ 开放环境的注册表），用 prime 命令行tool评测，用 prime-rl（Prime Intellect 的异步 RL trainer）训练。verifiers 和 Harbor 坐同一个座位——环境 / 评测侧——而且它明说一个环境对象身兼两职：「环境既可用于强化学习（RL）训练模型，也可用于能力评测、合成数据生成……」在评测和训练之间切换，环境本身一行都不用改。

smile = slime——RL 后训练trainer

v0.3.0 这一版让 slime 变成「agent-first」：新增专门的 slime/agent 模块（sandbox、trajectory merging、rollout 分组、OpenAI/Anthropic adapter）、黑盒 coding-agent RL 示例、全异步训练和delta weight sync。

统一框架：一个loop，三个part

每个 RL 训练步都是一个loop，三个part：sample（让agent尝试任务）、score（reward）、update（weight sync）。并用rollout 接口 链接在一起 (reward, token_ids, loss_mask)

# 这份契约的抽象形态——所有harness「生产」它，所有trainer「消费」它
rollout = (
    reward,      # 标量：这次尝试做得多好？
    token_ids,   # 模型实际采样出的 token（prompt + 回复）
    loss_mask,   # 逐 token 的 1/0：这个 token 要训练吗？（模型 = 1，环境 = 0）
)

Harbor（harbor-framework/harbor）主要任务是在sandbox里对着Task跑一个agent然后给出 score

2.2 Agent 契约：BaseAgent（setup → run）

每个脚手架都继承 BaseAgent 并实现两个异步方法。setup() 把agent的tool setup进运行中的container；run() 真正尝试任务，并边跑边把发生的事写进一个 context 对象（这样即使超时也能留下部分数据）。SUPPORTS_ATIF 声明它是否输出 Harbor 的 RL-ready trajectory格式（下文详述）。

class BaseAgent(ABC):
    SUPPORTS_ATIF: bool = False          # 是否输出 RL-ready 的 token trajectory？

    @abstractmethod
    async def setup(self, environment): ...        # 把tool装进container

    @abstractmethod
    async def run(self, instruction, environment, context):
        # 驱动任务；过程中把结果写进 `context`
        ...

agent只通过 environment.exec(...) 跟container对话。值得注意的是因为async它和container跑在不同进程里，这让agent逻辑可以在所有sandbox后端之间无缝迁移。

2.3 Environment ：一个接口，多种后端sandbox的可能

BaseEnvironment 是一个抽象类——「在container里执行命令」——带 exec、upload_dir/download_dir、start/stop 和一个 capabilities 描述符。exec 是所有人（agent、verifier、oracle）都可以使用的：

class BaseEnvironment(ABC):
    @abstractmethod
    async def start(self, force_build: bool): ...
    @abstractmethod
    async def stop(self, delete: bool): ...
    @abstractmethod
    async def exec(self, command, cwd=None, env=None,
                   timeout_sec=None, user=None) -> ExecResult: ...   # stdout/stderr/return_code

cloud sandbox才是重点。Trial 通过一个 EnvironmentFactory 选后端，只有真用到才lazily imports the SDK——本地 Docker，或云端 E2B / Modal / Daytona / Runloop / GKE / Novita / …。一次 coding-agent rollout 几乎全部时间都在等（等 LLM API、等命令、等container启动），所以它是 I/O 密集而非计算密集。

2.4 Terminus-2：ReAct agentloop harness

默认 Agent 是 Terminus-2，一个 ReAct 风格脚手架（ReAct = "Reason + Act"：思考、输出动作、读结果、重复）。只给模型一个 tmux 作为tool，因为几乎所有 CLI 程序都靠击键驱动，一个tool就基本覆盖了全部。每轮模型输出 JSON {analysis, plan, commands:[{keystrokes, duration}], task_complete}；

注意Terminus-2 是RL-aware ：True，这就意味着 collect_rollout_details=True 时它逐轮记录 prompt_token_ids、completion_token_ids 和 logprobs来避免token不一致。

从这里我们也可以看出，一个简易的ReAct风格的agent loop已经满足了绝大多数环境的需求。但是对于复杂环境还是得要一个复杂的agent loop/harness

2.5 Verifier：reward 是一个文件

Verifier 上传一个agent从未见过的测试脚本，在环境里执行，然后读脚本写到 reward.txt（或 reward.json）里的数字：

class Verifier(BaseVerifier):
    async def verify(self) -> VerifierResult:
        await self.environment.upload_dir(tests_dir, "/tests")   # agent永远看不到这些
        await self.environment.exec(test_script_command)         # 脚本写出 reward 文件
        rewards = self._parse_reward_json()  # 或 _parse_reward_text(): {"reward": 1.0}
        return VerifierResult(rewards=rewards)

2.6 Trial._run()：rollout 生命周期（run_agent → verify → teardown）

基类 Trial.run() 是一条严格兜底、容错的流水线：

1. _prepare()启动sandbox、健康检查、安装agent

2. _run()，因为_recover_outputs()的保护，所以即使 trial 被取消也能完成清理，几百个并发时不泄漏sandbox。

async def _run(self):
    await self._run_agent()          # 在超时控制下运行 agent.run()
    await self._upload_agent_logs()
    await self._collect_artifacts()  # 把结果快照搬出sandbox
    # SEPARATE 模式：判分前先拆掉agent环境（用全新的 verifier sandbox）
    await self._run_verifier()       # 测试脚本 → reward 文件 → VerifierResult
    # SHARED 模式：在同一container内判分，然后拆除
flowchart TD
    P["_prepare()<br/>启动sandbox · 健康检查 · 安装agent"] --> RA["_run_agent()<br/>超时控制下运行 agent.run()"]
    RA --> UL["_upload_agent_logs() + _collect_artifacts()<br/>把结果快照搬出sandbox"]
    UL --> RV["_run_verifier()<br/>测试脚本 → reward.txt → VerifierResult"]
    RV --> DONE(["reward ✅"])
    RA -.->|异常 / 超时| REC["_recover_outputs()<br/>抢救部分数据"]
    UL -.->|异常| REC
    RV -.->|异常| REC

虚线箭头是安全网：任何异常都仍会经过 _recover_outputs()，finally 块里的拆除被 asyncio.shield 保护，任何 trial 都能完成清理

2.7 ATIF：the trajectory format that makes a trial trainable

RL trainer要的是 token ID 和 loss mask。ATIF（Agent Trajectory Interchange Format）是 Harbor 的统一 JSON schema（当前 ATIF-v1.7，用 Pydantic 定义）。Trajectory 持有按序的 Step 列表；每步的 Metrics 可存 prompt_token_ids（模型读到的——mask置 0，无gradient）和 completion_token_ids（模型生成的——mask置 1）。存精确整数 ID 绕开了 re-tokenize 所造成的训练 / 推理不一致。

Step(step_id=2, source="agent",
     message="I'll run the tests.",
     metrics=Metrics(prompt_tokens=520, completion_tokens=80,
                     completion_token_ids=[1722, 310, 5533]))  # RL 关键字段

2.8 RL post-train from harbor：rollout 接口

RL 需要每次尝试的三样东西：reward、token ID、loss mask。Harbor 跑一个 Job 时三样都已经产出：

class HarborRolloutInterface(SomeRLFrameworkRolloutInterface):
    async def run(self, task_ids) -> list[Rollout]:
        job = Job(config=JobConfig(
            environment=EnvironmentConfig(type=EnvironmentType.DAYTONA),   # cloud sandbox，rollout 可扩展
            agents=[AgentConfig(name=AgentName.TERMINUS_2,
                                model_name="hosted_vllm/<model>",
                                kwargs={"base_url": "https://<vllm-server>"})],  # ← trainer自己的策略服务器
            orchestrator=OrchestratorConfig(n_concurrent_trials=32),       # 32 个慢 rollout 并行
            tasks=task_configs))
        result = await job.run()

        rollouts = []
        for tr in result.trial_results:
            reward    = tr.verifier_result.rewards.get("reward", 0)   # 来自 Verifier
            token_ids = tr.agent_result.metadata["token_ids"]         # 来自 ATIF
            mask_ids  = tr.agent_result.metadata["mask_ids"]          # Harbor 对 loss mask的叫法
            rollouts.append(Rollout(reward=reward, token_ids=token_ids, mask_ids=mask_ids))
        return rollouts

拿到精确 token 的两条路。要么在 vLLM 服务器出口拦截 ID（Miles/SkyRL 的路线），要么让agent在结果元数据里带回来（Terminus-2 的 collect_rollout_details）。两条都避免了重新分词漂移。SFT/RL trajectory导出从同一个 ATIF 文件：trajectory.json

3. verifiers——RL 环境库（聚焦 RL 后训练）

verifiers（Prime Intellect 出品，导入别名 vf）是一个构建 RL 环境的 Python 库。

环境是一个自包含的 Python 模块

用一个 Python 文件，暴露一个函数load_environment()并返回dataset、harness（the rollout loop that lets the model attempt each prompt）、Rubric（把尝试折算成 reward 的判分器）的环境对象。最小示例：

import verifiers as vf

def load_environment(**kwargs) -> vf.Environment:
    dataset = load_my_prompts()                  # 行：{"question": ..., "answer": ...}

    def correct_answer(completion, answer, parser, **kw) -> float:
        return 1.0 if parser.parse_answer(completion) == answer else 0.0

    rubric = vf.Rubric(funcs=[correct_answer], weights=[1.0])
    return vf.SingleTurnEnv(dataset=dataset, rubric=rubric, parser=vf.Parser())

这个模块就是pi其余生态的最小复用的模块：prime CLI 评测它（prime eval run my-env -m openai/gpt-4.1-mini -n 10），Environments Hub 分发它（prime env push，推到 2,500+ 开放环境的注册表），prime-rl 在它上面训练——评测和 RL 用的是同一个模块

环境类的层级

几乎每个环境都继承同一个基础agentloop。MultiTurnEnv 这个主干逐轮记录 token，遵循「模型说、环境答、重复」的循环直到停止条件触发。你只需要根据不同的 env 填入不同的env_response(messages, state)就可以知道「给定到目前为止的对话，环境回什么？」然后继承 token 记录、停止处理、超时和打分。

以下是上层建筑我们其实可以理解为harness：

  • SingleTurnEnv——max_turns=1 的 MultiTurnEnv：一问一答（上面的数学 / QA 例子）。
  • ToolEnv——把 env_response 实现为「执行模型刚调用的tool」。tool就是一个普通 Python 函数；verifiers 读它的类型注解 + docstring 生成模型瞄准的 JSON schema，逐个执行调用，把结果作为 tool 消息喂回去。模型回复时不再调用tool，回合即结束（一个 @vf.stop 谓词）。
  • StatefulToolEnv——加上隐藏注入参数。bash tool需要 sandbox_id，但模型不该看到它；StatefulToolEnv 把它从 schema 里藏起来（add_tool(tool, args_to_skip=["sandbox_id"])），调用时经 update_tool_args() 注入。模型写 {"command": "ls"}；环境在执行前把它变成 {"command": "ls", "sandbox_id": "..."}。
  • SandboxEnv / PythonEnv——把真实container句柄穿进tool的 StatefulToolEnv，用于必须隔离的代码执行。

共享agentloop的好处：每个具体环境都逐轮携带 prompt/completion 边界，RL侧因此能正确构造 loss mask（模型的 token 有gradient，tool/环境的 token 没有）。整个阶梯是一条继承链，每一级恰好加一个能力：

flowchart TD
    E["Environment — 基类：数据集 + harness + Rubric"] --> MT["MultiTurnEnv<br/>「说/答/重复」的主干；填 env_response()"]
    MT --> ST["SingleTurnEnv<br/>= max_turns=1 的 MultiTurnEnv（数学 / QA）"]
    MT --> TE["ToolEnv<br/>env_response =「执行模型调用的tool」"]
    TE --> STE["StatefulToolEnv<br/>+ 隐藏注入参数（如 sandbox_id）"]
    STE --> SE["SandboxEnv / PythonEnv<br/>+ 真实container句柄，做隔离代码执行"]

Rubric——把奖励写成带weight、带名字的函数

Rubric is a list of small reward functions plus a weight per function。reward = Σ score_i · weight_i。每个function都声明自己想要的参数然后Rubric 用 inspect.signature 准确的递上。

weight = 0.0 可以让一个function变成指标（只记录、不训练）。crash isolation是build in的：任何奖励函数内部的异常记 0.0，不会杀死 rollout。

For grouped GRPO (Group Relative Policy Optimization)，Rubric.score_group 先算每个 rollout 的 reward 和组均值，再设 state["advantage"] = reward − mean(group)

现成rubric：

  • MathRubric——自动加一个 correct_answer 函数：抽取模型的 \boxed{...} 答案，用 math_verify 库对照标准答案（符号等价，所以 1/2 匹配 0.5）。验证跑在 ProcessPoolExecutor 里，5 秒软超时 / 120 秒硬超时，病态表达式挂不死整个运行。形状：
def correct_answer(completion, answer, parser, **kw) -> float:
    response = parser.parse_answer(completion)        # MaybeThinkParser + extract_boxed_answer
    return 1.0 if math_verify.verify(answer, response) else 0.0   # 符号等价
  • JudgeRubric——给无法代码化的东西打分（「这个摘要忠实吗？」）：去问第二个模型。它暴露一个 judge(prompt, completion, answer, state) 方法（默认用便宜的 gpt-4.1-nano，按 rollout 缓存——两个奖励函数都咨询它也只付一次 API 钱）；你写个极小的奖励函数，把它的 "yes"/"no" 裁决映射成 1.0/0.0。
  • RubricGroup——把几个完整的 rubric 相加（一个正确性 rubric + 一个独立的安全 rubric）。

Parser——抽出要判分的答案

Parser 从模型的原始文本里抽出可判分的答案。

v1「可组合」模型——让harness跨任务复用

v1 把它们拆成三个可复用的部件，让一个agent脚手架可以驱动很多任务：

  • Taskset——任务是什么（data、prompts、success rewards）；可复用
  • Harness——描述模型怎么尝试任意任务（安装 + 运行命令、从哪里读指令、端点拦截）；可复用
  • Toolset——动作空间

在实验性的 ComposableEnv 里，环境就是taskset，harness之间的连接件：

class ComposableEnv(CliAgentEnv):
    def __init__(self, taskset, harness, **kwargs):
        kwargs["dataset"] = taskset.get_dataset          # taskset 拥有数据……
        kwargs.setdefault("rubric", taskset.get_rubric())#   ……以及奖励
        super().__init__(run_command=harness.run_command, **kwargs)  # harness 拥有agent怎么跑
        # rollout 时：把任务指令写到 harness.instruction_path，
        #             把 harness.system_prompt 写到 harness.system_prompt_path，
        #             安装agent、运行它，最后让 rubric 打分

Harness 是个普通 dataclass（install_script、run_command、instruction_path、sandbox_spec……）。Taskset 拥有 get_instruction()、get_sandbox_spec()、setup() 和 evaluate()。ComposableEnv 把任务的指令写进 harness 声明的路径，于是一个静态的 run_command 读到的是每个任务各自的指令。结果是一张网格——任意 harness × 任意 taskset，靠config接线：

RL Post-train

以下是 verifiers 作出的优化：

靠拦截的 TITO。那么verifiers 的解决方案是token id 和 loss mask 直接来自 inference（openai_chat_completions_token 客户端），trainer看到的就是模型实际采样出的 token。在 RLM harness 里能看到字面写法：

# 在agent的 run_command 里、sandbox内部：
export OPENAI_API_KEY="${OPENAI_API_KEY:-intercepted}"   # 占位符：这个调用被「捕获」，而不是被认证
rlm "$(cat /task/instruction.md)"

因为agent的调用被路由到trainer的inference server，rollout 模型 == training模型，sampling是 on-policy 的，精确的 token id + logprobs 被记录在案。同一个 harness 用 keep_trajectory_step 丢弃 subagent calls（tagged X-RLM-Depth > 0），只让parent agent的轮次驱动policy gradient

flowchart LR
    A["sandbox中的 CLI agent<br/>OPENAI_API_KEY='intercepted'"] -->|"POST /v1/chat/completions"| I["interceptor<br/>（trainer的端点）"]
    I -->|转发| P["policy inference server<br/>(vLLM / SGLang)"]
    P -->|"回复 + 精确 token_ids + logprobs"| I
    I -->|"回复（agent毫无察觉）"| A
    I ==>|"记录 token_ids、logprobs、mask<br/>绝不重新分词"| TR["trajectory → trainer"]

关键在interceptor的双重身份：对agent透明（就是个 OpenAI 兼容端点），却悄悄留下策略输出的精确 token 和 logprobs——这是从一个黑盒 CLI agent拿到训练/推理一致gradient的办法。

Environments Hub 闭环：任何环境写一次就能推送（prime env push）、被任何人安装（prime env install）、评测（prime eval run）、在 prime-rl 下训练——全用同一个模块，因为跨过接口的契约只有 (reward, token_ids, loss_mask)。

4. smile（slime）——RL trainer（聚焦 v0.3.0 agent-first 更新）

v0.3.0 的头条：专门的 slime/agent 模块

v0.3.0（tag v0.3.0，2026-05-31）把它整合进一个可复用的 slime/agent 模块。训练在真实环境中行动的模型（跑 shell 命令、改文件、调tool、跨多轮重试），而不是只输出一段文本。一次agent rollout 不再是一次生成，而是一整个回合（episode）：启动sandbox、几十个模型轮次、跑一遍测试套件——通常 30 秒到几分钟，所以要 32–100 个并行跑。本版本基于 SGLang v0.5.12.post1 和 Megatron commit 1dcf0dafa 发布。

5-stage agent rollout loop

你在一个用 --custom-generate-function-path 注册的自定义 generate 函数里实现这个循环；slime/agent 模块提供可复用的部件。形状如下：

async def generate(args, sample, sampling_params):
    # 阶段 1 —— 打开一个隔离的sandbox会话（每次尝试一个一次性container）
    async with E2BSandbox(image) as sb:                 # sandbox协议：exec / read_file / write_file
        # 阶段 2 —— 经协议adapter运行agent的多轮交互
        adapter = AnthropicAdapter(tokenizer, sglang_url, tool_parser, reasoning_parser)
        adapter.open_session(session_id, sampling_defaults=sampling_params)
        run_agent_scaffold(sandbox=sb, base_url=adapter.app)   # agent以为自己在调 Anthropic
        # 阶段 3 —— 把录下的轮次回收成可训练的 token 片段
        segments = await adapter.finish_session(session_id)    # list[TokenSegment]
        # 阶段 4 —— 在「全新clean sandbox」里给这次尝试打分（reward 无法作弊）
        reward = grade(git_diff(sb), in_clean_sandbox=True)
        # 阶段 5 —— 给trainer产出 Sample
        return fan_out_sample_segments(sample, segments, reward, tokenizer)

视觉上，这个循环是两个sandbox、中间用一个 git diff 桥接——agent在脏sandbox里干活，判分却在全新sandbox里进行，所以agent没法篡改自己的测试：

flowchart LR
    S1["① 打开dirty sandbox<br/>（一次性container）"] --> S2["② 经 OpenAI/Anthropic adapter<br/>运行agent多轮"]
    S2 --> S3["③ 回收轮次 →<br/>TokenSegment（merge_turns）"]
    S2 -.->|"git diff"| S4
    S3 --> S5
    S4["④ 在全新clean sandbox打分<br/>应用 diff + 跑测试 → reward"] --> S5["⑤ fan_out_sample_segments<br/>→ Sample(tokens, reward, loss_mask)"]
    S5 ==>|"交给 GRPO trainer"| OUT([trainer])

sandbox（阶段 1）

  1. 是个极小的异步 Protocol——exec(cmd) -> (exit_code, stdout, stderr)、read_file、write_file——自带的后端是 E2BSandbox（包装 e2b.AsyncSandbox）。
  2. 每次 RPC 都经过 _rpc_retry并且对瞬态客户端故障（ConnectTimeout、PoolTimeout、SSLError、h2 重置）指数退避重试最多 3 次（因为cloud sandbox在大规模下又慢又抖）。
  3. 因为在独立的clean sandbox（阶段 4）里判分，agent改不了自己的测试环境也就无法作弊。

OpenAI / Anthropic adapter——伪装的 API 服务器，捕获精确 token

把 base URL 指向一个伪装成官方 API 的本地adapter。运用现成的脚手架（Claude Code、OpenAI Agents SDK 应用）照常 POST /v1/messages，这样就可以使用现成的脚手架作为 harness

adapter收到请求，用模型的 chat template 把对话渲染成 input_ids，带 return_logprob=True 调 SGLang /generate，再按官方 API 原生的 JSON/SSE 形状回复。

env = {
    "ANTHROPIC_BASE_URL":  adapter_url,   # 指向 slime 的adapter，不是 Anthropic
    "ANTHROPIC_AUTH_TOKEN": session_id,   # session id 伪装成 Bearer token 偷运进来
    "ANTHROPIC_MODEL":     "slime-actor",
}

因为SGLang 生成回复的时候返回的是 (logprob, token_id)，所以adapter留下了精确的sampled token id 和per-token log-probabilities记成一个 TurnRecord（prompt_ids、output_ids、finish_reason、output_log_probs）。

session_id 作为 X-SMG-Routing-Key prefix，让同一episode的所有turn都落在同一个 SGLang worker 上且复用它的prefix cache（--router-policy consistent_hashing）。

trajectory merging——把多轮缝成一条带mask的序列，且不重新re-tokenizer

问题。agent的一个回合不是干净的「一问一答」。第 1 轮是 prompt₁ → output₁；第 2 轮的 prompt 是「prompt₁ + output₁ + tool结果」——每一轮都把前面的内容全部重念一遍，录下来的是一摞互相重叠的片段。而trainer只吃一条扁平的 token 序列 + 一个 0/1 mask（标明哪些 token 要训练）。trajectory merging干的就是这个「拍平」的活。

因为分词器不可往返的特性（比如 "don't" 既能切成 don+'t，也能切成 do+n't——文字一样，id 不同）。id 一错位，事先算好的对数概率就贴到错的 token 上，gradient被悄悄污染。

merge_turns 的做法逐轮扫过去，已经在序列里的部分跳过，只追加每轮新增的内容，边追加边打标签——环境写的（tool结果）mask 0，模型写的（output）mask 1：

def merge_turns(turns):
    prompt_ids = turns[0].prompt_ids        # 第一轮的 prompt = 这个片段的 prompt
    response_ids, loss_mask, log_probs = [], [], []
    for turn in turns[1:]:
        suffix = turn.prompt_ids[len(prompt_ids):]          # 超出基准 prompt 的全部内容
        matched = common_prefix_len(response_ids, suffix)   # 我们自己先前的输出有多少原样重现
        if matched < len(response_ids):                     # 前缀漂移：prompt 在输出中途分叉
            zero_out_straddling_output_spans(matched)       # 拒绝对无法证实的 token 反传
            response_ids, loss_mask, log_probs = truncate_to(matched)
        context_tail = suffix[matched:]                     # 真正新的环境上下文
        response_ids += context_tail
        loss_mask    += [0] * len(context_tail)             # mask 0：模型「读」的 token
        log_probs    += [0.0] * len(context_tail)
        response_ids += turn.output_ids                     # 模型自己的生成
        loss_mask    += [1] * len(turn.output_ids)          # mask 1：模型「写」的 token
        log_probs    += turn.output_log_probs
    return TokenSegment(prompt_ids, response_ids, loss_mask, log_probs)

两轮的回合拍平之后长这样——只有模型自己写的 token 拿到gradient：

flowchart TD
    subgraph REC["adapter录下的两轮（注意：第 2 轮把第 1 轮全部重念了一遍）"]
        T1["第 1 轮：[ prompt₁ ] → [ output₁ ]"]
        T2["第 2 轮：[ prompt₁ + output₁ + tool结果 ] → [ output₂ ]"]
    end
    REC ==>|"merge_turns 重放：重复的跳过，只追加新内容"| FLAT
    subgraph FLAT["拍平后的一条序列（trainer吃的就是它）"]
        direction LR
        A["prompt₁<br/>『修复 utils.py 的测试』<br/>题目 · 不训练"] --> B["output₁<br/>『我先看看文件…』<br/>mask 1 ✅ 有gradient"]
        B --> C["tool结果<br/>『文件内容 / 报错』<br/>mask 0 ❌ 环境注入"]
        C --> D["output₂<br/>『是差一错误，打补丁…』<br/>mask 1 ✅ 有gradient"]

安全措施：前缀漂移。如果第 2 轮的 prompt 在 output₁ 的中间就和录音对不上了，对不上的那段就不是可信的训练目标——代码把跨越分叉点的输出的mask和对数概率清零，并截掉缝不上的尾巴。宁可少训一点，也不训错的。最终的不变式：mask 1 ⇔ 真实的模型 token ⇔ 真实的对数概率；其余位置全为 0。

Rollout 分组——给 GRPO 用的 group_ids

GRPO 用一个极其简单的基线替掉了 PPO ：对同一个 prompt 生成若干次尝试，每次跟自己兄弟们的平均比。对一组 n 次尝试、奖励 r1,…,rn，优势在组内标准化：Ai = (ri − mean(r)) / std(r)。为此trainer必须知道哪些样本是兄弟——同一个 prompt 的每次尝试都盖上同一个 group_id。v0.3.0 特意把这个字段从 rollout_ids 改名为 group_ids：

  • group_id——「我属于哪个 prompt 的组？」同一个 prompt 的 n_samples 次不同尝试共享。GRPO 按它分桶。
  • rollout_id——「我是哪一条trajectory的片段？」当合并把一个回合切成 subagent / wipe / final 几段时，这些片段共享。

第二个 id 来自 fan_out_sample_segments，阶段 5 的辅助函数。一条trajectory可以扇出成多个训练样本（一个subagent分支、一个压缩前的片段）；它把 reward 均分，并给每个兄弟同一个 rollout_id，让按 rollout 求均值的归约器把这条trajectory只数一次：

def fan_out_sample_segments(sample, segments, reward, tokenizer, rollout_id=None):
    k = len(segments)
    per_segment_reward = reward / max(1, k)                 # 均分 reward
    shared_rollout_id  = rollout_id or sample.index         # 兄弟共享一个 rollout_id
    out = []
    for i, segment in enumerate(segments):
        sub = sample if i == 0 else copy.copy(sample)
        write_segment_to_sample(sub, segment, per_segment_reward, tokenizer)
        sub.rollout_id = shared_rollout_id
        sub.metadata = {**sub.metadata, "segment_idx": i, "num_segments": k}
        out.append(sub)
    return out

让慢速agent rollout 变得划算的系统级特性

agent rollout 又慢又参差——一个 30 秒，另一个 5 分钟。同步训练里 GPU 就在这种参差里空转：要么等最慢的 rollout，要么等weight传完。v0.3.0 用四个特性把这些等待逐个消灭：

特性消灭的等待怎么做到（一句话）
全异步训练等一批里最慢的 rollout后台维持一个永不停的生成「暖池」（AsyncRolloutWorker 始终补满在途任务），trainer只捞已完成的；用 train_async.py 开启。代价是轻度 off-policy，用 --use-tis 矫正
可变全局 batch给短trajectory填充、把长trajectory截断每步消费手头实际有的样本数，不凑整 N
delta weight sync每步广播 100B+ 完整weight字节级 diff 只传改动位置——约 3% 密度，355B 模型约 5 GB（--update-weight-mode delta，走 nccl 或 disk 传输）
Actor-Critic 共置PPO 的 critic、actor 各占一组 GPUPPO 重构后两者共享 GPU。（GRPO 干脆不要 critic——所以它是默认算法）

一句话总结：前两个让RL永远有活干，后两个让weight传输和硬件不再白等白占。

5. Agent Infra——如何构建一个优秀的 Agent Infra，以及它如何与 RL Infra 共同迭代

5.1 为什么需要 Agent Infra

在开放世界的复杂任务中，agent能够调用tool、执行命令、观察反馈，并据此迭代行动。无论是修改文件、管理进程，还是操作浏览器，每一次交互都在实质性地改变环境状态——这正是agent补足模型在实时感知与执行能力上短板的方式。这种交互模式的转变，直接催生了对sandbox环境的需求。简单任务或许可以用无状态sandbox应对：每次tool调用都启动一个全新container、执行完立即销毁，天然隔离、易于扩展。但真实的agent任务往往需要有状态sandbox：模型在第 1 轮创建了一个文件，第 2 轮需要读取它；第 3 轮启动了一个服务，第 4 轮需要向它发请求。状态必须在多轮交互之间延续。这带来一连串 Infra 挑战：sandbox的生命周期如何管理？长时间运行的会话如何处理超时和异常？大规模并发时如何高效调度资源？

这些不是假设性问题——本案例研究里的每个系统都在某处给出了回答：Harbor 的 Trial 永远在被 shield 保护的 finally 里拆掉container，几百个并发 trial 也不泄漏sandbox（§2.6）；slime 把每次sandbox RPC 都包进 _rpc_retry 做 3 次指数退避重试，正是因为cloud sandbox在大规模下又慢又抖（§4）；而「有状态的终端」在工程上的标准答案就是一个 tmux 持久会话——恰好是 Terminus-2 暴露的那个唯一tool（§2.4）——而不是一连串彼此独立、无状态的 run_command 调用。

除了sandbox之外，模型与环境之间的交互设计同样是agent场景的关键组成部分。模型通过什么接口与环境交互？tool的动作空间（Action Space）如何定义，才能既表达力强又易于学习？执行结果应该以什么形式反馈给模型——原始的 stdout/stderr，结构化的 JSON，还是经过截断和摘要的文本？这些设计决策会直接影响模型的任务完成能力：好的交互设计能让模型更准确地理解环境状态、更高效地规划下一步行动；糟糕的设计则会导致信息丢失、上下文膨胀，甚至让模型陷入死循环。成熟的agent栈会把这些当作最重要的配置项——tool输出截断上限、观察超时、上下文超限的显式退出状态——Terminus-2 为长回合内置上下文摘要器，也是同一个原因（§2.4）。

这些问题加起来，构成了一个全新的 Infra 层：Agent Infra——一切介于模型和外部世界之间的东西：sandbox环境、tool调用、状态管理、trajectory记录。它是在传统 LLM Infra（推理服务 + 训练）之外需要单独构建的新模块。而它正是把「应用/harness → 数据 → 训练 → 更好的应用/harness」这个闭环接起来的基础设施：让研究者能够在真实环境中运行agent、收集trajectory数据、评估任务完成度，再在结果上训练。Harbor 把这个闭环写得很明白——给agent打分的那个 Job，同时产出 RL rollout 和 SFT trajectory：一次评测运行既给出分数，也给出训练下一代模型的信号（§2.8）。

flowchart LR
    APP["🤖 应用<br/>agent在有状态sandbox里<br/>尝试真实任务"] -->|"trajectory + reward"| DATA["📊 数据<br/>ATIF / 精确 token id<br/>/ loss mask"]
    DATA -->|"RL rollout + SFT trajectory"| TRAIN["🏋️ 训练<br/>GRPO / SFT"]
    TRAIN -->|"新weight"| MODEL["✨ 更好的模型"]

那么，如何设计一个完善的 Agent Infra？本节余下部分从 Infra 的视角分析 Harbor 和 verifiers 的特点，提炼一个优秀的 Agent Infra 应该暴露的核心抽象，然后走进 slime agent-first 的 v0.3.0，探寻在新一代 agentic 范式下，RL 框架应该如何与agent层一起迭代。

5.2 从 Harbor 学到什么：握住基准，握住 agent loop

Harbor 由发布 Terminal-Bench（2025 年 5 月）的同一个团队构建，是 Terminal-Bench 2.0 的官方运行框架。它的采用逻辑很直白：Terminal-Bench 成了前沿模型的标尺——Gemini 3 报告 TB 2.0 得分 54.2%（2025 年 11 月）、GPT-5.1-Codex-Max 报告 58.1%（2025 年 11 月）、Claude Opus 4.6 宣称「在 agentic 编码评测 Terminal-Bench 2.0 上取得最高分」（2026 年 2 月）、DeepSeek-V3.2 报告 46.4%（2025 年 12 月）。当数据集成为事实上的行业标尺，拥有它的运行框架自然继承它的用户：对很多用户来说，选择 Harbor 就是在选择 Terminal-Bench 的准确性和便捷性。Harbor 自己 README 的快速上手命令就是 harbor run --dataset terminal-bench@2.0 --agent claude-code --model anthropic/claude-opus-4-1 --n-concurrent 4。

细看这份公信力从哪来，三项投入很突出。(1) 数据集的上下游构建：基准 adapter 把现有评测套件（SWE-Bench、AIME、BFCL……）导入 Harbor 格式，并用对齐实验（parity experiment）——对原版与适配版做统计重叠检验——来验证；外加注册表（harbor datasets list、harbor publish）和每个任务用 oracle 标准解做正确性自检。(2) 白盒 agent loop：Terminus-2 只暴露一个 tmux tool，每轮记录成 ATIF，开 collect_rollout_details=True 后逐轮捕获 prompt_token_ids / completion_token_ids / logprobs（§2.4）——Anthropic 在 Claude Sonnet 4.5 的评测方法里甚至写明「所有报告分数均使用默认 agent 框架（Terminus 2）」。(3) tool的个性化处理：每个脚手架保留自己的 AgentConfig kwargs（解析器、api_base、摘要旋钮），ATIF 把每个agent的原生动作如实记录成 ToolCall——Terminus-2 的击键被记为 function_name="bash_command", arguments={keystrokes, duration}——而不是强行统一成一套tool。

代价侧也是真实的：编写一个任务意味着写至少 4 个必需件——task.toml、instruction.md、environment/（Dockerfile 或 compose）、tests/test.sh（必须写出 reward 文件）——加上推荐的 solution/solve.sh，实践中约 5 件；使用 Harbor 还要学一族子命令（带 -d/-p/-a/-m/-e/-n 的 harbor run，以及 harbor datasets list、harbor view、harbor trial start、harbor publish）。

总结一（来自 Harbor）。在 Harbor 的引力真正来源处投入：数据集上下游构建（adapter + 对齐验证 + 注册表）、第一方白盒 agent loop（全程插桩、RL-ready）、tool的个性化处理（如实记录原生动作，不要拍平成统一tool集）。

5.3 从 verifiers 学到什么：一个文件、一行命令、一份契约

verifiers 把打包方式整个倒了过来。环境是一个自包含的 Python 模块——三个文件（暴露 load_environment() 的 my_env.py、pyproject.toml、README），用 prime env init my-env 脚手架生成，一行命令端到端跑通：prime eval run my-env -m openai/gpt-4.1-mini -n 10（还会自动安装）。对比第一天的上手体验：Harbor 要求你编写 4–5 个任务件、学习好几个子命令；verifiers 只要求一个文件里的一个函数和一条命令。用户喜欢一行命令就能跑起来的东西——抽象层把底层实现差异完全屏蔽掉了。

这份单一契约也正是它能异构地规模化的原因：Environments Hub 上有 2,500+ 个环境，横跨数学、编码、游戏、搜索、tool调用、多模态，全部暴露同一个 load_environment() 入口；prime-rl 的三个并发进程（inference server / 编排器 / FSDP trainer）能在其中任何一个上训练；自家的证明是 INTELLECT-2（32B，经全球分布式 RL 训练）和 INTELLECT-3（100B+ MoE）。两个来自源文档的诚实注脚：v1 的 Taskset/Harness 迁移在那 2,500+ 个环境上仍是进行中状态；公开的规模化证据是架构性的（三进程设计、重要性采样矫正），而非已发表的吞吐数字。

总结二（来自 verifiers）。把环境做成一个文件、一条命令的单元，让用户完全不用碰底层实现；把入口标准化成一份契约，让成千上万的异构环境和任意trainer自由组合；再加一个注册表，生态就成了飞轮。

5.4 综合——优秀 Agent Infra 的五个性质

性质今天谁做到了我们拿走什么
环境稳定、干净——环境和底层实现由我们统一管理Harbor 给每个任务钉死container镜像；slime 在全新clean sandbox里判分，reward 无法作弊（§4）干净的镜像/环境是可信 reward 的前提——必须端到端握在自己手里
结构上可移植（structural portable）verifiers 把 Harbor 的任务和 agent harness整体搬走（HarborTaskset、terminus-harbor、opencode-harbor，§3）；Miles 实现了 Harbor 的 rollout 接口（swe-agent-v2）任务包和 agent loop 应该以「数据 + 薄类」的形式跨栈移植，而不是重写
Async and lazily importsprime-rl 的三进程解耦（§3）；slime 的全异步暖池（§4）；Miles 用 partial rollout + 过采样对付长尾trajectory；lazily imports来应对密集I/O from harboragent rollout 又慢又参差——Infra 绝不能让trainer等最慢的那个
易用（easy to use）verifiers 的一文件/一命令体验；Harbor 的一个 flag 换sandbox后端（-e daytona）复杂性住在抽象线以下，永远不要漏到上面
Token 级忠实——绝不重新分词Harbor 用 ATIF 存精确 id（§2.7）；verifiers 用拦截做 TITO（§3）；slime 用伪装adapter + trajectory merging（§4）token id 在生成那一刻当场记录、之后只搬运不重建——这是gradient不被悄悄污染的前提

这五个性质里，第五个是唯一一个三个系统各自重新发明了一遍的——同一条铁律（绝不重新分词），三个系统在三个不同的层面执行：

系统在哪一层解决具体方案
Harbor记录与交接格式层白盒agent自己记：Terminus-2 开 collect_rollout_details=True，逐轮记下 token id + logprobs，存进标准化的 ATIF（trajectory.json）；trainer直接从结果元数据里拿（§2.7–2.8）
verifiersAPI 端点层（拦截）TITO：token id 和 loss mask直接来自inference server；对黑盒 CLI agent，把每次 LLM 调用逼回trainer自己的端点——interceptor对agent透明，却当场留下精确 token id + logprobs（OPENAI_API_KEY="intercepted"，§3）
slime引擎原生接口 + 多轮合并层伪装adapter直连 SGLang /generate（return_logprob=True），拿到 (logprob, token_id) 对；再用 merge_turns 重放对齐把整个回合拍平——对不上的 token 宁可清零也不猜（前缀漂移保护，§4）

三个角度互补：Harbor 信任白盒agent自己上报，verifiers 在传输路径上拦截（黑盒也适用），slime 从引擎拿原始数据、并保证多轮拼接之后依然忠实（Harbor 文档自己也承认拦截路线——§2.8 的「两条路」）。无论走哪条路，铁律只有一条：token id 在生成那一刻被记录；之后的每个环节只搬运它，绝不重建它。

5.5 三个核心抽象：Task / Agent loop / Tool

剥掉本案例研究里每个系统的品牌外衣，剩下的都是同样三个抽象，架在第四个底座（sandbox/运行时）之上：

  • Task ↔ 基准（benchmark）。它定义任务描述、初始状态、成功条件——且结果必须可验证对错。在 Harbor 里是任务目录（instruction.md + task.toml + environment/ + 写出 reward.txt 的测试）；在 verifiers 里是数据集 + Rubric；两边的主心骨都是 RLVR 的「真实测试过了吗」。

  • Agent loop ↔ 产品侧的 Agent 实现。它封装行为逻辑——LLM 调用、tool选择、多轮交互。我们倾向白盒复刻而非黑盒调用，理由有三：(1) 现有产品面向用户会做兜底处理，这是好的用户体验，但在评测里会掩盖模型的真实能力；(2) 黑盒没有缝隙插入自定义指标和 reward；(3) 复刻成本通常不高——一个带tool注册表、重试和截断旋钮的插桩 ReAct 循环，正是 Terminus-2 已经是的东西，而 mini-swe-agent 这类极简脚手架只有百行左右的量级。黑盒封装（Claude Code、Gemini CLI、Codex）在追求广度和速度时仍然有用——但它在能力测量和 reward 插入上的代价是真实的，§5.7 会用 slime 自己的例子具体展示。

  • Tool ↔ agent可调用的原子操作——RL 的动作空间（Action Space）。不同 Agent 产品的tool设计各有特色：Terminus-2 的单个 tmux 窗格、Claude Code 的文件/编辑tool、verifiers ToolEnv 的「tool就是一个 Python 函数」（外加 StatefulToolEnv 的隐藏注入参数）。Tool 抽象应该保留每个 Agent 原有的tool定义，而非强制统一——Infra 的职责是如实记录它们（像 ATIF 用原生 ToolCall 形状那样），而不是拍平它们。

    AL["🤖 Agent loop — 白盒复刻的<br/>产品侧行为逻辑"] --> RT

5.6 把sandbox层握在自己手里

Prime Intellect 给出的启示是垂直整合：算力市场 + Sandboxes + Environments Hub + verifiers + prime-rl + Lab/Evaluations + 自家的 INTELLECT 模型——明确定位为「自我改进agent的开放栈」（§3）。如果我们也想要属于自己的 RL-to-Env 生态，建立自己的sandbox Infra 是值得，因为在 agentic RL 里sandbox位于每次 rollout 的关键路径上：slime 的 coding_agent_rl 每次尝试要启动两个sandbox（干活 + 干净判分），再乘上每个 issue 的 --n-samples-per-prompt 8；每次 RPC 都要过 _rpc_retry，规模一大瞬态sandbox故障就是家常便饭（§4）。sandbox的启动成功率和启动延迟会在整条流水线上成倍放大——这正是 RL 后训练效率真正能大幅提升的部分。

而风险是低的，因为sandbox是上一代互联网验证过的成熟基础设施。优化一个已被验证的底座是工程问题，不是研究问题。再加上结构可移植性的agent infra设计可以迅速移植其他agent infra的benchmark。例如verifiers 用一个薄薄的 Taskset 类就把 Harbor 的 Terminal-Bench 任务和 agent harness搬走了

5.7 RL Infra × Agent Infra 的有机迭代——以 slime v0.3.0 为例

站在RL-infra的座位上，通往环境有两条路线：路线① 自建——trainer自带的 agent 模块自己启动sandbox、自己判分；路线② 第三方 harness——对着 Harbor 或 verifiers 实现 rollout 接口。

既然路线②存在，路线①为什么重要？因为有些能力只有在环境侧和trainer侧被一起设计时才存在——v0.3.0 就是这类协同设计的一份目录：

coding_agent_rl 唯一的软肋是它训练的是一个黑盒agent。黑盒agent产品的兜底处理可能掩盖模型真实能力；没有缝隙插入逐步指标或 reward——奖励只能挂在最后（git diff → 测试），无法进入循环内部。

这正是本节标题承诺的有机迭代：agent 层暴露需求（trajectory片段、会话亲和、sandbox抖动、机群横向扩展）→ RL 层长出特性（可变 batch、路由策略、重试、增量同步）→ 反过来又让更丰富的 agent 任务变得划算。两层都无法孤立设计；同时坐在两个座位上的团队迭代最快。
