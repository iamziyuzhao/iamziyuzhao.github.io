0. Introduction

A good agent/evaluation infrastructure must provide what RL needs. This article begins with Harbor in Section 2 and verifiers in Section 3. Along the way, it explains their RL post-training features and gives a clear, high-level framework. Section 4 then examines smile's approach to agent training and shows how environments, agents, and CLIs should interact with RL infrastructure to improve training. Finally, Section 5 draws on all three systems to identify the key elements of good agent infrastructure and two possible directions for future RL infrastructure.

Harbor — the agent-eval / RL-environment harness

Harbor is the harness that answers one question: "Set up a task and an agent, and tell me how well it did." We can describe it with six abstractions — Task (the instruction + files), Environment (a standard sandbox, using local Docker or a cloud provider), Agent (the scaffold being tested), Verifier (runs tests → produces a reward), Trial (one rollout that produces one reward), and Job (a whole batch of trials). Harbor's role is on the environment/evaluation side: it runs the agent and grades it. Its slogan sums up the whole wiki: "a trial is a rollout that produces a reward."

verifiers — the RL-environment + eval library

verifiers is a library for writing self-contained RL environments as small Python modules. Each environment = dataset + rollout harness + Rubric (a set of weighted reward functions), exposed through classes like SingleTurnEnv, MultiTurnEnv, and ToolEnv. These environments are published to the Environments Hub (a registry of 2,500+ open environments), evaluated with the prime command-line tool, and used for training with prime-rl (Prime Intellect's asynchronous RL trainer). verifiers has the same role as Harbor — the environment/evaluation side — and clearly states that one environment object serves both purposes: "Environments can be used for training models with reinforcement learning (RL), evaluating capabilities, generating synthetic data..." You do not need to change the environment when switching between evaluation and training.

smile = slime — the RL post-training trainer

v0.3.0 is the release that made slime "agent-first": it added a dedicated slime/agent module (sandboxes, trajectory merging, rollout grouping, and OpenAI/Anthropic adapters), a black-box coding-agent RL example, fully asynchronous training, and delta weight sync.

The unifying frame: one loop, three parts

Every RL training step is one loop with three parts: sample (let the agent attempt the task), score (produce a reward), and update (sync the weights). The parts are linked by the rollout interface: (reward, token_ids, loss_mask).

# the contract, in the abstract — every harness PRODUCES this, every trainer CONSUMES it
rollout = (
    reward,      # scalar: how good was this attempt?
    token_ids,   # the exact tokens the model sampled (prompt + response)
    loss_mask,   # per-token 1/0: train on this token? (model = 1, environment = 0)
)

Harbor (harbor-framework/harbor) mainly runs an agent on a Task in a sandbox and then gives it a score.

2.2 The Agent contract: BaseAgent (setup → run)

Every scaffold subclasses BaseAgent and implements two asynchronous methods. setup() installs the agent's tools in the running container. run() attempts the task and records what happens in a context object as it runs, so a timeout still leaves partial data. SUPPORTS_ATIF states whether the agent outputs Harbor's RL-ready trajectory format (explained below).

class BaseAgent(ABC):
    SUPPORTS_ATIF: bool = False          # does it emit RL-ready token traces?

    @abstractmethod
    async def setup(self, environment): ...        # install tools into the container

    @abstractmethod
    async def run(self, instruction, environment, context):
        # drive the task; write results into `context` as you go
        ...

The agent communicates with the container only through environment.exec(...). Because the interface is asynchronous, the agent and container can run in separate processes. This lets the same agent logic work with any sandbox backend.

2.3 Environment: one interface, many sandbox backends

BaseEnvironment is a single abstract class — "run commands in a container" — with exec, upload_dir/download_dir, start/stop, and a capabilities descriptor. exec is the method everyone (agent, verifier, oracle) can use:

class BaseEnvironment(ABC):
    @abstractmethod
    async def start(self, force_build: bool): ...
    @abstractmethod
    async def stop(self, delete: bool): ...
    @abstractmethod
    async def exec(self, command, cwd=None, env=None,
                   timeout_sec=None, user=None) -> ExecResult: ...   # stdout/stderr/return_code

Cloud sandboxes are the key here. A Trial picks a backend through an EnvironmentFactory, which imports the SDK only when it is needed — local Docker, or cloud E2B / Modal / Daytona / Runloop / GKE / Novita / …. A coding-agent rollout spends nearly all its time waiting for the LLM API, commands, or containers to start, so it is I/O-bound, not compute-bound.

2.4 Terminus-2: the ReAct agent-loop harness

The default Agent is Terminus-2, a ReAct-style scaffold (ReAct = "Reason + Act": think, produce an action, read the result, and repeat). The model gets only one tool: a tmux-based terminal. Because nearly every CLI program can be controlled with keystrokes, this one tool covers most needs. On each turn, the model outputs JSON: {analysis, plan, commands:[{keystrokes, duration}], task_complete}.

Terminus-2 is also RL-aware. With collect_rollout_details=True, it records per-turn prompt_token_ids, completion_token_ids, and logprobs to prevent token mismatches.

A simple ReAct-style agent loop meets the needs of most environments. Complex environments, however, still need a more capable agent loop or harness.

2.5 The Verifier: the reward is a file

A Verifier uploads a test script the agent never saw, runs it inside the environment, and reads the number the script wrote to reward.txt (or reward.json):

class Verifier(BaseVerifier):
    async def verify(self) -> VerifierResult:
        await self.environment.upload_dir(tests_dir, "/tests")   # agent never sees these
        await self.environment.exec(test_script_command)         # script writes a reward file
        rewards = self._parse_reward_json()  # or _parse_reward_text(): {"reward": 1.0}
        return VerifierResult(rewards=rewards)

2.6 Trial._run(): the rollout lifecycle (run_agent → verify → teardown)

The base Trial.run() is a carefully protected, fault-tolerant pipeline:

1. _prepare() starts the sandbox, checks its health, and installs the agent.

2. _run() runs with _recover_outputs() as a safety net. Even if a Trial is canceled, cleanup still finishes, so hundreds of concurrent Trials do not leak sandboxes.

async def _run(self):
    await self._run_agent()          # agent.run() under a timeout
    await self._upload_agent_logs()
    await self._collect_artifacts()  # snapshot results out of the sandbox
    # SEPARATE mode tears down the agent env before grading (fresh verifier sandbox)
    await self._run_verifier()       # test script → reward file → VerifierResult
    # SHARED mode grades in the same container, then tears down
flowchart TD
    P["_prepare()<br/>boot sandbox · healthcheck · install agent"] --> RA["_run_agent()<br/>agent.run() under a timeout"]
    RA --> UL["_upload_agent_logs() + _collect_artifacts()<br/>snapshot results out of the sandbox"]
    UL --> RV["_run_verifier()<br/>test script → reward.txt → VerifierResult"]
    RV --> DONE(["reward ✅"])
    RA -.->|exception / timeout| REC["_recover_outputs()<br/>salvage partial data"]
    UL -.->|exception| REC
    RV -.->|exception| REC
    REC --> TD
    DONE --> TD["finally: teardown (shielded)<br/>— always runs, no leaked sandboxes"]

The dashed arrows are the safety net: any exception still routes through _recover_outputs(), and teardown in the finally block is protected by asyncio.shield, so every Trial finishes cleanup.

2.7 ATIF: the trajectory format that makes a trial trainable

An RL trainer needs token IDs and a loss mask. ATIF (Agent Trajectory Interchange Format) is Harbor's unified JSON schema (currently ATIF-v1.7, defined with Pydantic). Trajectory holds an ordered list of Steps. Each Step's Metrics can store prompt_token_ids (what the model read — mask 0, no gradient) and completion_token_ids (what it generated — mask 1). Storing exact integer IDs avoids the training/inference mismatch caused by re-tokenization.

Step(step_id=2, source="agent",
     message="I'll run the tests.",
     metrics=Metrics(prompt_tokens=520, completion_tokens=80,
                     completion_token_ids=[1722, 310, 5533]))  # the RL-critical field

2.8 RL post-training from Harbor: the rollout interface

RL needs three things per attempt: a reward, the token IDs, and a loss mask. Harbor already produces all three when it runs a Job:

class HarborRolloutInterface(SomeRLFrameworkRolloutInterface):
    async def run(self, task_ids) -> list[Rollout]:
        job = Job(config=JobConfig(
            environment=EnvironmentConfig(type=EnvironmentType.DAYTONA),   # cloud sandbox; lets rollouts scale
            agents=[AgentConfig(name=AgentName.TERMINUS_2,
                                model_name="hosted_vllm/<model>",
                                kwargs={"base_url": "https://<vllm-server>"})],  # the trainer's own policy server
            orchestrator=OrchestratorConfig(n_concurrent_trials=32),       # 32 slow rollouts in parallel
            tasks=task_configs))
        result = await job.run()

        rollouts = []
        for tr in result.trial_results:
            reward    = tr.verifier_result.rewards.get("reward", 0)   # from the Verifier
            token_ids = tr.agent_result.metadata["token_ids"]         # from ATIF
            mask_ids  = tr.agent_result.metadata["mask_ids"]          # Harbor's name for the loss mask
            rollouts.append(Rollout(reward=reward, token_ids=token_ids, mask_ids=mask_ids))
        return rollouts

Two ways to get the exact tokens. Either intercept the IDs as they leave the vLLM server (the approach used by Miles/SkyRL), or have the agent return them in the result metadata (Terminus-2's collect_rollout_details). Both approaches avoid re-tokenization drift. SFT and RL trajectories are exported from the same ATIF file: trajectory.json.

3. verifiers — the RL-environment library (focus: RL post-training)

verifiers (by Prime Intellect, import alias vf) is a Python library for building RL environments.

An environment is a self-contained Python module

One Python file exposes one function load_environment() and returns an environment object made of a dataset, a harness (the rollout loop that lets the model attempt each prompt), and a Rubric (the grader that turns an attempt into a reward). A minimal example:

import verifiers as vf

def load_environment(**kwargs) -> vf.Environment:
    dataset = load_my_prompts()                  # rows: {"question": ..., "answer": ...}

    def correct_answer(completion, answer, parser, **kw) -> float:
        return 1.0 if parser.parse_answer(completion) == answer else 0.0

    rubric = vf.Rubric(funcs=[correct_answer], weights=[1.0])
    return vf.SingleTurnEnv(dataset=dataset, rubric=rubric, parser=vf.Parser())

This module is the smallest reusable unit in the rest of the Prime Intellect ecosystem. The prime CLI evaluates it (prime eval run my-env -m openai/gpt-4.1-mini -n 10), the Environments Hub distributes it (prime env push, into a registry of 2,500+ open environments), and prime-rl trains on it. Evaluation and RL use the same module.

The environment class hierarchy

Almost every environment inherits the same base agent loop. The MultiTurnEnv base class records tokens one turn at a time and repeats this loop until a stop condition is met: "The model speaks, and the environment responds." For each environment, you only implement env_response(messages, state) to answer one question: "Given the conversation so far, what should the environment return?" Token recording, stop handling, timeouts, and scoring are inherited.

The higher-level classes act as harnesses:

  • SingleTurnEnv — MultiTurnEnv with max_turns=1: one question, one answer (the math/QA case above).
  • ToolEnv — implements env_response as "run the tools the model just called." A tool is a normal Python function. verifiers reads its type hints and docstring to build the JSON schema shown to the model, runs each call, and returns the results as tool messages. The episode ends when the model replies without calling a tool (a @vf.stop predicate).
  • StatefulToolEnv — adds hidden, injected arguments. A bash tool needs a sandbox_id, but the model shouldn't see it; StatefulToolEnv hides it from the schema (add_tool(tool, args_to_skip=["sandbox_id"])) and injects it at call time via update_tool_args(). The model writes {"command": "ls"}; the env turns it into {"command": "ls", "sandbox_id": "..."} before execution.
  • SandboxEnv / PythonEnv — StatefulToolEnvs that pass a real container handle to the tool, for code execution that must be isolated.

The shared agent loop provides an important benefit: every environment keeps the prompt/completion boundary for each turn. The RL system can therefore build the loss mask correctly (model tokens receive gradients; tool and environment tokens do not). The full hierarchy is one inheritance chain, and each level adds exactly one capability:

flowchart TD
    E["Environment — base: dataset + harness + Rubric"] --> MT["MultiTurnEnv<br/>the speak/answer/repeat trunk; fill in env_response()"]
    MT --> ST["SingleTurnEnv<br/>= MultiTurnEnv with max_turns=1 (math / QA)"]
    MT --> TE["ToolEnv<br/>env_response = 'run the tools the model called'"]
    TE --> STE["StatefulToolEnv<br/>+ hidden injected args (e.g. sandbox_id)"]
    STE --> SE["SandboxEnv / PythonEnv<br/>+ a real container handle for isolated code exec"]

Rubric — rewards as weighted, named functions

A Rubric is a list of small reward functions, with a weight for each function. reward = Σ score_i · weight_i. Each function declares only the arguments it needs, and the Rubric passes exactly those arguments by using inspect.signature.

A weight of 0.0 turns a function into a metric (logged, not trained on). Crash isolation is built in: an exception inside any reward function scores 0.0 rather than killing the rollout.

For grouped GRPO (Group Relative Policy Optimization), Rubric.score_group computes each rollout's reward and the group mean, then sets state["advantage"] = reward − mean(group).

Ready-made rubrics:

  • MathRubric — automatically adds a correct_answer function. It extracts the model's \boxed{...} answer and checks it against the reference answer with the math_verify library (using symbolic equivalence, so 1/2 matches 0.5). Verification runs in a ProcessPoolExecutor with a 5-second soft timeout and a 120-second hard timeout, so a difficult expression cannot freeze the whole run. It has this form:
def correct_answer(completion, answer, parser, **kw) -> float:
    response = parser.parse_answer(completion)        # MaybeThinkParser + extract_boxed_answer
    return 1.0 if math_verify.verify(answer, response) else 0.0   # symbolic equivalence
  • JudgeRubric — grades things that cannot easily be checked with code ("Is this summary faithful?") by asking a second model. It provides a judge(prompt, completion, answer, state) method. By default, it uses the inexpensive gpt-4.1-nano and caches the result for each rollout, so if two reward functions use it, only one API call is made. You write a small reward function that maps its "yes"/"no" decision to 1.0/0.0.
  • RubricGroup — sums several complete rubrics (a correctness rubric + a separate safety rubric).

Parser — extracting the answer to grade

A Parser pulls the gradable answer out of the model's raw text.

The v1 "Composable" model — reuse the harness across tasks

v1 separates the system into three reusable parts, so one agent scaffold can handle many tasks:

  • Taskset — what the task is (data, prompts, success rewards); reusable
  • Harness — describes how a model attempts an arbitrary task (install + run command, where it reads the instruction, endpoint interception); reusable
  • Toolset — the action space

In the experimental ComposableEnv, the environment connects the taskset and the harness:

class ComposableEnv(CliAgentEnv):
    def __init__(self, taskset, harness, **kwargs):
        kwargs["dataset"] = taskset.get_dataset          # taskset owns the data...
        kwargs.setdefault("rubric", taskset.get_rubric())#   ...and the reward
        super().__init__(run_command=harness.run_command, **kwargs)  # harness owns how the agent runs
        # at rollout time: write task instruction -> harness.instruction_path,
        #                  write harness.system_prompt -> harness.system_prompt_path,
        #                  install agent, run it, then let the rubric score

Harness is a plain dataclass (install_script, run_command, instruction_path, sandbox_spec, …). Taskset owns get_instruction(), get_sandbox_spec(), setup(), and evaluate(). ComposableEnv writes the task's instruction into the path the harness declares, so a static run_command reads a per-task instruction. The result is a grid — any harness × any taskset, wired by config:

RL post-training

Here are the optimizations verifiers made:

verifiers uses interception for TITO: token IDs and the loss mask come directly from inference (through the openai_chat_completions_token client), so the trainer sees the exact tokens the model sampled. The RLM harness shows this directly:

# from the agent's run_command, inside the sandbox:
export OPENAI_API_KEY="${OPENAI_API_KEY:-intercepted}"   # placeholder: the call is captured, not authenticated
rlm "$(cat /task/instruction.md)"

Because the agent's calls are routed to the trainer's inference server, the rollout model is the training model, sampling is on-policy, and the exact token IDs and log probabilities are recorded. The same harness uses keep_trajectory_step to remove subagent calls (tagged X-RLM-Depth > 0), so only the parent agent's turns drive the policy gradient.

flowchart LR
    A["CLI agent in sandbox<br/>OPENAI_API_KEY='intercepted'"] -->|"POST /v1/chat/completions"| I["interceptor<br/>(trainer's endpoint)"]
    I -->|forwards| P["policy inference server<br/>(vLLM / SGLang)"]
    P -->|"reply + exact token_ids + logprobs"| I
    I -->|"reply (agent none the wiser)"| A
    I ==>|"records token_ids, logprobs, mask<br/>NO re-tokenization"| TR["trajectory → trainer"]

The interceptor has two roles. To the agent, it looks like a normal OpenAI-compatible endpoint. At the same time, it records the exact tokens and log probabilities produced by the policy. This makes it possible to get gradients that are consistent between training and inference from a black-box CLI agent.

The Environments Hub closes the loop: once an environment is written, it can be pushed (prime env push), installed by anyone (prime env install), evaluated (prime eval run), and trained with prime-rl — all using the same module, because the only interface contract is (reward, token_ids, loss_mask).

4. smile (slime) — the RL trainer (focus: the v0.3.0 agent-first update)

The v0.3.0 headline: a dedicated slime/agent module

v0.3.0 (tag v0.3.0, 2026-05-31) brings these features together in one reusable slime/agent module. It trains models that act in real environments — running shell commands, editing files, calling tools, and retrying over many turns — instead of producing one block of text. An agent rollout is no longer a single generation. It is a complete episode: start a sandbox, run dozens of model turns, and execute a test suite. An episode often takes 30 seconds to several minutes, so 32–100 episodes run in parallel. This version is based on SGLang v0.5.12.post1 and Megatron commit 1dcf0dafa.

The 5-stage agent rollout loop

You implement this loop in a function registered with --custom-generate-function-path — a custom generate function. The slime/agent module provides the reusable parts. It looks like this:

async def generate(args, sample, sampling_params):
    # STAGE 1 — open an isolated sandbox session (one throwaway container per attempt)
    async with E2BSandbox(image) as sb:                 # Sandbox Protocol: exec / read_file / write_file
        # STAGE 2 — run the agent's many turns through a protocol adapter
        adapter = AnthropicAdapter(tokenizer, sglang_url, tool_parser, reasoning_parser)
        adapter.open_session(session_id, sampling_defaults=sampling_params)
        run_agent_scaffold(sandbox=sb, base_url=adapter.app)   # agent thinks it calls Anthropic
        # STAGE 3 — collect recorded turns into trainable token segments
        segments = await adapter.finish_session(session_id)    # list[TokenSegment]
        # STAGE 4 — score the attempt in a FRESH clean sandbox (the reward cannot be gamed)
        reward = grade(git_diff(sb), in_clean_sandbox=True)
        # STAGE 5 — emit a Sample for the trainer
        return fan_out_sample_segments(sample, segments, reward, tokenizer)

Visually, the loop uses two sandboxes connected by a git diff. The agent works in a dirty sandbox, but grading happens in a fresh one, so the agent cannot modify its own tests:

flowchart LR
    S1["① open dirty sandbox<br/>(one throwaway container)"] --> S2["② run agent's many turns<br/>via OpenAI/Anthropic adapter"]
    S2 --> S3["③ collect turns →<br/>TokenSegment (merge_turns)"]
    S2 -.->|"git diff"| S4
    S3 --> S5
    S4["④ score in a FRESH clean sandbox<br/>apply diff + run tests → reward"] --> S5["⑤ fan_out_sample_segments<br/>→ Sample(tokens, reward, loss_mask)"]
    S5 ==>|"to GRPO trainer"| OUT([trainer])

The sandbox (stage 1):

  1. It is a minimal asynchronous Protocol: exec(cmd) -> (exit_code, stdout, stderr), read_file, and write_file. The included backend is E2BSandbox, which wraps e2b.AsyncSandbox.
  2. Every RPC goes through _rpc_retry. It retries temporary client failures (ConnectTimeout, PoolTimeout, SSLError, and h2 resets) up to three times with exponential backoff, because cloud sandboxes can be slow and unreliable at scale.
  3. Grading happens in a separate clean sandbox (stage 4). The agent cannot change its own test environment, so it cannot cheat.

OpenAI / Anthropic adapter — a fake API server that captures exact tokens

Point the base URL to a local adapter that acts like the real API. Existing scaffolds, such as Claude Code or an OpenAI Agents SDK application, send requests to /v1/messages just as they normally would. This allows existing scaffolds to serve as the harness.

The adapter receives the request, uses the model's chat template to turn the conversation into input_ids, calls SGLang /generate with return_logprob=True, and responds in the API's normal JSON/SSE format.

env = {
    "ANTHROPIC_BASE_URL":  adapter_url,   # points at slime's adapter, not Anthropic
    "ANTHROPIC_AUTH_TOKEN": session_id,   # session id passed as the Bearer token
    "ANTHROPIC_MODEL":     "slime-actor",
}

Because SGLang returns (logprob, token_id) pairs as it generates, the adapter keeps the exact sampled token ids and per-token log-probabilities, recorded as a TurnRecord (prompt_ids, output_ids, finish_reason, output_log_probs).

The session_id is forwarded as the X-SMG-Routing-Key prefix, so all turns of one episode land on the same SGLang worker and reuse its prefix cache (--router-policy consistent_hashing).

Trajectory merging — stitch many turns into one masked sequence, without re-tokenizing

The problem. An agent's episode is not a simple question and answer. Turn 1 is prompt₁ → output₁. Turn 2's prompt is "prompt₁ + output₁ + a tool result." Every turn re-reads everything that came before, so the recording contains overlapping pieces. The trainer, however, uses one flat token sequence plus a 0/1 mask that shows which tokens to train on. Trajectory merging creates this flat sequence.

Because tokenizers are not round-trip safe (e.g. "don't" can split as don+'t or do+n't — same text, different ids), once the ids shift, the precomputed log-probs attach to the wrong tokens and the gradient is silently corrupted.

What merge_turns does: walk the turns in order; skip whatever is already in the sequence, append only each turn's new content, labeling as it goes — environment-written tokens (tool results) get mask 0, model-written tokens (outputs) get mask 1:

def merge_turns(turns):
    prompt_ids = turns[0].prompt_ids        # first turn's prompt = segment prompt
    response_ids, loss_mask, log_probs = [], [], []
    for turn in turns[1:]:
        suffix = turn.prompt_ids[len(prompt_ids):]          # everything beyond the base prompt
        matched = common_prefix_len(response_ids, suffix)   # how much is our own prior output reappearing
        if matched < len(response_ids):                     # PREFIX DRIFT: prompt diverged mid-output
            zero_out_straddling_output_spans(matched)       # do not backprop tokens that cannot be verified
            response_ids, loss_mask, log_probs = truncate_to(matched)
        context_tail = suffix[matched:]                     # genuinely-new environment context
        response_ids += context_tail
        loss_mask    += [0] * len(context_tail)             # mask 0: tokens the model READ
        log_probs    += [0.0] * len(context_tail)
        response_ids += turn.output_ids                     # the model's own generation
        loss_mask    += [1] * len(turn.output_ids)          # mask 1: tokens the model WROTE
        log_probs    += turn.output_log_probs
    return TokenSegment(prompt_ids, response_ids, loss_mask, log_probs)

A two-turn episode is flattened like this — only the model's own tokens receive gradients:

        T2["Turn 2: [ prompt₁ + output₁ + tool result ] → [ output₂ ]"]
    end

Safety measure: prefix drift. If turn 2's prompt stops matching the recording inside output₁, the mismatched section is not a trustworthy training target. The code sets the mask and log probabilities to zero for any output that crosses the point of difference, then removes the tail it cannot join correctly. It is better to train on less data than on incorrect data. The final rule is: mask 1 ⇔ a real model token ⇔ a real log probability; all other positions are 0.

Rollout grouping — group_ids for GRPO

GRPO replaces PPO with a very simple baseline: for one prompt, generate several attempts and compare each one with the average of the group. For a group of n attempts with rewards r1,…,rn, the advantage is standardized within the group: Ai = (ri − mean(r)) / std(r). The trainer must therefore know which samples belong together, so every attempt for the same prompt receives the same group_id. v0.3.0 deliberately renamed this field from rollout_ids to group_ids:

  • group_id — "Which prompt's group do I belong to?" The n_samples different attempts for one prompt share this ID. GRPO uses this field to group samples.
  • rollout_id — "which single trajectory am I a fragment of?" Shared across the segments of one attempt when merging splits an episode into subagent / wipe / final pieces.

That second id comes from fan_out_sample_segments, the stage-5 helper. One trajectory can fan out into several training samples (a subagent branch, a pre-compaction segment); it splits the reward uniformly and gives every sibling the same rollout_id so a per-rollout-mean reducer counts the trajectory exactly once:

def fan_out_sample_segments(sample, segments, reward, tokenizer, rollout_id=None):
    k = len(segments)
    per_segment_reward = reward / max(1, k)                 # split reward uniformly
    shared_rollout_id  = rollout_id or sample.index         # siblings share one rollout_id
    out = []
    for i, segment in enumerate(segments):
        sub = sample if i == 0 else copy.copy(sample)
        write_segment_to_sample(sub, segment, per_segment_reward, tokenizer)
        sub.rollout_id = shared_rollout_id
        sub.metadata = {**sub.metadata, "segment_idx": i, "num_segments": k}
        out.append(sub)
    return out

The systems-level features that make slow agent rollouts affordable

Agent rollouts are slow and highly uneven — one may take 30 seconds, while another takes 5 minutes. In synchronous training, this leaves GPUs idle while they wait for the slowest rollout or for weights to transfer. v0.3.0 uses four features to remove these waits one by one:

FeatureThe wait it removesHow (one sentence)
Fully asynchronous trainingwaiting for the slowest rollout in a batcha background generation "warm pool" runs continuously (AsyncRolloutWorker keeps tasks in flight); the trainer collects only completed work. Enable it with train_async.py. The tradeoff is mildly off-policy training; --use-tis corrects for this
Variable global batch sizepadding short / truncating long trajectorieseach step uses however many samples are actually available; it does not wait to fill a fixed batch of N
Delta weight syncbroadcasting a full 100B+ checkpoint every stepa bytewise diff ships only the changed positions — ~3% density, ~5 GB for a 355B model (--update-weight-mode delta, transported via nccl or disk)
Actor-critic colocationusing separate GPU groups for PPO's critic and actorthe PPO refactor lets them share GPUs. (GRPO skips the critic entirely — which is why it is the default)

In short: the first two keep the RL system supplied with work; the last two reduce weight-transfer time and idle hardware.

5. Agent Infra — what it takes to build a good one, and how it co-evolves with RL infra

5.1 Why Agent Infra exists

In complex, open-world tasks, an agent calls tools, runs commands, observes feedback, and changes its next action based on what it sees. Whether it edits files, manages processes, or controls a browser, every interaction changes the environment's state. This helps overcome a model's limited real-time awareness and ability to act. This new interaction pattern creates a need for sandboxes. Simple tasks may use a stateless sandbox: start a fresh container for each tool call, run the call, and then destroy the container. This is naturally isolated and easy to scale. Real agent tasks, however, often need a stateful sandbox. The model may create a file in turn 1 and read it in turn 2, then start a service in turn 3 and call it in turn 4. State must continue across turns. This creates several infrastructure challenges: How should the sandbox lifecycle be managed? How should long-running sessions handle timeouts and errors? How should resources be scheduled efficiently at large scale?

These are real engineering questions, and every system in this case study answers them somewhere. Harbor's Trial always removes the container in a protected finally block, so hundreds of concurrent Trials do not leak sandboxes (§2.6). slime wraps every sandbox RPC in _rpc_retry, with up to three retries and exponential backoff, because cloud sandboxes can be slow and unreliable at scale (§4). In practice, a "stateful terminal" means a persistent tmux session — the one tool exposed by Terminus-2 (§2.4) — instead of a series of separate, stateless run_command calls.

Beyond the sandbox, the design of the interaction between the model and environment is just as important. What interface does the model use? How should the tool Action Space be defined so it is both powerful and easy to learn? How should results be returned — as raw stdout/stderr, structured JSON, or shortened and summarized text? These choices directly affect how well the model completes tasks. Good interaction design helps the model understand the environment and plan its next step. Poor design loses information, makes the context too large, or traps the model in a loop. Mature agent systems treat tool-output limits, observation timeouts, and explicit exits for context overflow as key settings. Terminus-2 includes a context summarizer for long episodes for the same reason (§2.4).

Together, these problems create a new infrastructure layer: Agent Infra — everything between the model and the outside world, including sandboxes, tool calls, state management, and trajectory recording. It must be built in addition to traditional LLM infrastructure for inference and training. Agent Infra closes the loop "application/harness → data → training → better application/harness": run agents in real environments, collect trajectories, grade the results, and train on them. Harbor makes this loop clear. The same Job that grades an agent also produces RL rollouts and SFT trajectories, so one evaluation run provides both a score and a training signal for the next model (§2.8).

    DATA -->|"RL rollouts + SFT trajectories"| TRAIN["🏋️ Training<br/>GRPO / SFT"]

How do we design a complete Agent Infra? The rest of this section examines Harbor and verifiers from an infrastructure perspective, identifies the core abstractions a good Agent Infra should provide, and then uses slime's agent-first v0.3.0 to show how an RL framework can evolve together with the agent layer.

5.2 What Harbor teaches: own the benchmark, own the agent loop

Harbor was built by the same team that released Terminal-Bench in May 2025, and it is the official harness for Terminal-Bench 2.0. The reason for its adoption is clear: Terminal-Bench became a standard benchmark for leading models. Gemini 3 reports 54.2% on TB 2.0 (Nov 2025), GPT-5.1-Codex-Max reports 58.1% (Nov 2025), Claude Opus 4.6 claims "the highest score on the agentic coding evaluation Terminal-Bench 2.0" (Feb 2026), and DeepSeek-V3.2 reports 46.4% (Dec 2025). When a dataset becomes the de facto industry standard, its official harness naturally attracts the same users. For many users, choosing Harbor means choosing the accuracy and convenience of Terminal-Bench. Harbor's README uses this quick-start command: harbor run --dataset terminal-bench@2.0 --agent claude-code --model anthropic/claude-opus-4-1 --n-concurrent 4.

Three investments explain this credibility. (1) End-to-end dataset infrastructure: benchmark adapters import existing suites such as SWE-Bench, AIME, and BFCL into Harbor. They are validated with parity experiments — statistical overlap tests between the original and adapted versions. Harbor also provides a registry (harbor datasets list, harbor publish) and uses oracle solutions to check each task. (2) A white-box agent loop: Terminus-2 exposes one tmux tool, records every turn as ATIF, and uses collect_rollout_details=True to capture prompt_token_ids, completion_token_ids, and logprobs on every turn (§2.4). Anthropic's Claude Sonnet 4.5 evaluation method even states that "all scores reported use the default agent framework (Terminus 2)." (3) Tool handling for each agent: every scaffold keeps its own AgentConfig settings, such as the parser, api_base, and summarization controls. ATIF records each agent's original actions as ToolCalls — Terminus-2's keystrokes become function_name="bash_command", arguments={keystrokes, duration} — instead of forcing every agent into one toolset.

There is also a real cost. Creating a task requires at least four pieces: task.toml, instruction.md, environment/ (a Dockerfile or Compose file), and tests/test.sh (which must write the reward file). A recommended solution/solve.sh brings the practical total to about five pieces. Harbor users must also learn several commands: harbor run with -d/-p/-a/-m/-e/-n, plus harbor datasets list, harbor view, harbor trial start, and harbor publish.

Lesson 1 (from Harbor). Invest in what makes Harbor attractive: end-to-end dataset infrastructure (adapters + parity validation + a registry), a first-party white-box agent loop (fully instrumented and RL-ready), and tool handling for each agent (record original actions accurately instead of flattening them into one toolset).

5.3 What verifiers teaches: one file, one command, one contract

verifiers uses a different packaging model. An environment is a self-contained Python module with three files: my_env.py, which exposes load_environment(); pyproject.toml; and a README. prime env init my-env creates this structure, and one command runs it from start to finish: prime eval run my-env -m openai/gpt-4.1-mini -n 10. The command even installs the environment automatically. Compare the first-time experience: Harbor asks users to create 4–5 task files and learn several commands, while verifiers asks for one function in one file and one command. Users like tools that run with a single command. The abstraction completely hides differences in the underlying implementation.

The single contract also lets verifiers support many different environments at scale. The Environments Hub hosts more than 2,500 environments across math, coding, games, search, tool use, and multimodal tasks. Every environment exposes the same load_environment() entry point. The three concurrent prime-rl processes — inference server, orchestrator, and FSDP trainer — can train on any of them. Prime Intellect's own examples are INTELLECT-2 (32B, trained with globally distributed RL) and INTELLECT-3 (100B+ MoE). The sources also give two important limits: migration to the v1 Taskset/Harness model is still in progress across those 2,500+ environments, and the public evidence for scaling is architectural — the three-process design and importance-sampling correction — rather than published throughput numbers.

Lesson 2 (from verifiers). Make the environment a one-file, one-command unit so users never need to work with the underlying implementation. Standardize one entry-point contract so thousands of different environments can work with any trainer. Add a registry, and the ecosystem becomes self-reinforcing.

5.5 The three core abstractions: Task / Agent loop / Tool

Remove the product names, and every system in this case study has the same three abstractions. They rest on a fourth base layer: the sandbox/runtime.

  • Task ↔ the benchmark. It defines the task description, initial state, and success conditions — and the result must be verifiably right or wrong. In Harbor, this is the task directory: instruction.md + task.toml + environment/ + tests that write reward.txt. In verifiers, it is the dataset + Rubric. Both are built around RLVR's main question: "Did the real tests pass?"

  • Agent loop ↔ the Agent implementation used by the product. It contains the behavior logic: LLM calls, tool selection, and multi-turn interaction. We prefer white-box reimplementation over black-box use for three reasons. (1) Production agents include user-facing fallback handling. This improves the user experience but can hide the model's real ability during an evaluation. (2) A black box provides no place to add custom metrics or rewards inside the loop. (3) Reimplementation is often not very expensive. An instrumented ReAct loop with a tool registry, retries, and output limits is exactly what Terminus-2 provides, and simple scaffolds such as mini-swe-agent are only about a hundred lines long. Black-box wrappers for Claude Code, Gemini CLI, or Codex are still useful for speed and broad coverage. However, they make capability measurement and reward insertion harder, as §5.7 shows with slime's example.

  • Tool ↔ an individual action the agent can call — the RL Action Space. Agent products use different tool designs: Terminus-2 has one tmux pane, Claude Code has file and editing tools, and a tool in verifiers ToolEnv is a normal Python function. StatefulToolEnv can also inject hidden arguments. The Tool abstraction should keep each agent's original tool definitions instead of forcing them into one design. The infrastructure should record them accurately, as ATIF does with native ToolCall structures, rather than flattening them.

5.6 Owning the sandbox layer

Prime Intellect demonstrates vertical integration: a compute marketplace + Sandboxes + Environments Hub + verifiers + prime-rl + Lab/Evaluations + its own INTELLECT models. It describes this as "the open stack for self-improving agents" (§3). If we want our own RL-to-Environment ecosystem, building our own sandbox infrastructure is worthwhile because every agentic RL rollout depends on the sandbox. slime's coding_agent_rl starts two sandboxes for every attempt — one for work and one for clean grading — and runs eight attempts per issue with --n-samples-per-prompt 8. Every RPC goes through _rpc_retry, because temporary sandbox failures are common at scale (§4). The effects of sandbox startup success and latency are multiplied across the whole pipeline. This is where RL post-training throughput can improve substantially.

The risk is low because sandboxing is mature infrastructure, already proven by the previous generation of internet systems. Improving a proven foundation is an engineering problem, not a research problem. With a structurally portable Agent Infra design, we can also move benchmarks from other Agent Infra systems quickly. For example, verifiers moved Harbor's Terminal-Bench tasks and agent harness with one thin Taskset class.

5.7 RL Infra × Agent Infra co-evolution — slime v0.3.0 as a case study

From the RL infrastructure perspective, there are two ways to reach an environment. Route ①: build it internally — the trainer's own agent module starts sandboxes and grades attempts. Route ②: use a third-party harness — implement the rollout interface for Harbor or verifiers.

The only weakness of coding_agent_rl is that it trains a black-box agent. A black-box agent product's fallback handling can hide the model's real ability, and there is no place to add per-step metrics or rewards. The reward can only be assigned at the very end (git diff → tests), never inside the loop.

This is the co-evolution described above: the agent layer reveals needs (trajectory segments, session affinity, sandbox failures, and larger machine fleets) → the RL layer adds features (variable batch size, routing policies, retries, and delta sync) → those features make more complex agent tasks practical. Neither layer can be designed alone. Teams that control both layers can iterate fastest.
